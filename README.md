## 📖 About

This repository presents a systematic study of a widely deployed desktop software licensing scheme — **Cloud-Verified Licensing (CVL)** — covering its security model, potential attack surface, and corresponding hardening measures. Schemes in this class typically share these traits:

- The client connects to a remote verification server at startup to validate subscription status of a license key
- A hybrid cryptographic protocol is commonly used: client-generated session key + asymmetric transport + symmetric encrypted response
- The client binary is often hardened by commercial code virtualization protectors (VMP-class packers)
- The client holds and caches authorization state and cryptographic material locally

This study presents a generalized five-stage security assessment methodology for such schemes, fully **de-identified**, along with a defensive hardening checklist from the defender's perspective. All example code is either an **educational skeleton** or a **self-contained local lab** — by design, it operates only on simulated data generated by this repository itself and was not developed against any real-world product.

## 🎯 Motivation

- CVL schemes are widely adopted in desktop software, yet their security models rest on common misconceptions (e.g., "commercial packers equal security" or "HTTPS equals tamper-proofing")
- Once client-side weaknesses in a licensing protocol are systematically analyzed, vendors can usually remediate them at low cost; unanalyzed, the risk may persist indefinitely
- To provide a systematic reference for licensing-system developers, security auditors, and CTF players

## 🔬 Methodology Overview (Five Stages)

| Stage | Name | Goal | Key Techniques |
|-------|------|------|----------------|
| Ⅰ | Reconnaissance | Map the target's verification topology | netstat / DNS observation / pcap analysis |
| Ⅱ | Network-Layer Classification | Assess MITM feasibility | Certificate pinning test / direct-IP fallback detection |
| Ⅲ | In-Memory Material Location | Obtain session key material | Cross-process read-only scan / ciphertext trial-decryption |
| Ⅳ | Protocol Forgery Verification | Examine the client trust model | Byte-aligned response rewriting (proof of concept) |
| Ⅴ | Steady-State Ops & Reporting | Reproducibility and disclosure | Environment snapshots / responsible disclosure |

Full treatment in [docs/methodology.md](docs/methodology.md).

## 🔐 Corresponding Defenses (Quick View)

1. **Server-side authoritative decisions**: adjudicate subscription status server-side; avoid shipping parseable long-term expiry fields to the client
2. **Response signing**: sign verification responses with an asymmetric key; clients verify with a built-in public key to resist MITM rewriting
3. **Certificate pinning + fail-closed**: pin certificates and fail the connection on mismatch; be cautious with hardcoded-IP fallback paths
4. **Key lifecycle management**: wipe session keys after use, lock memory, minimize plaintext residency
5. **Defense in depth**: commercial packers (VMP-class) mainly raise static-analysis cost and are not a substitute for protocol-layer security design

Details in [docs/defense.md](docs/defense.md).

## 🧪 About the Example Code

Every example takes one of two forms:

- **Educational skeleton**: demonstrates standard usage of public Windows APIs (e.g., cross-process memory reading); users supply their own legally licensed test target
- **Self-contained lab**: the repository ships its own mock verification server and mock client ciphertext; the demo operates only on locally generated data and was not developed against any real-world product

```bash
# Quick tour of the self-contained lab
cd examples
python 04_demo_target_generator.py   # generate local mock ciphertext
python 05_forge_concept_demo.py      # demo the decrypt→rewrite→re-encrypt principle
```

Requirements: Python 3.8+, `cryptography` (`pip install cryptography`). Example 03 requires [mitmproxy](https://mitmproxy.org/).
